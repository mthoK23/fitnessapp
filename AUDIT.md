# FitTrack audit and rewrite

Audit date: 28 September 2026. Scope: tracked React source, routes, browser storage, forms, calculations, styling, build configuration and dependency tree. The original repository had no API or server. This is a source review and regression test exercise, not an external penetration test.

## Findings in the original application

| Severity | Finding and evidence in the original source | Consequence | Rewrite |
| --- | --- | --- | --- |
| Critical | `src/features/user/AuthContext.js`: registration writes `{username, password}` to `users`; the entire user is also written to `currentUser`. | Passwords are readable by same-origin scripts and anyone with access to browser storage. | Passwords are hashed on the server using salted scrypt; only public user fields leave the API. No credentials are stored in browser storage. |
| Critical | `AuthContext.js`: any parseable `currentUser` makes `isAuthenticated` true; all authorization is in React. | Editing local storage bypasses login. There is no trusted identity or data-access boundary. | Random opaque server sessions, hashed session tokens at rest, HttpOnly/SameSite cookies, server authorization on every data endpoint, seven-day expiry and server-side logout. |
| High | `src/features/user/AppContext.js`: effects both load and persist data on user/auth changes. Persistence sees the previous render's state before the loading effect's updates render. | Signing in or changing accounts can overwrite existing records with empty or another account's data. | Server owns persistence. Client replaces a complete session snapshot after successful requests; no storage-writing effects. Mutations verify the displayed account ID to catch cross-tab changes. |
| High | `src/features/workouts/Workouts.jsx`: schedules use the unscoped key `scheduledWorkouts`; `unit` is also global. | Accounts share schedules and preferences. | Planned and completed workouts live in the authenticated user's collection. Consistent metric units throughout. |
| High | `src/services/nutritionixService.js`: `REACT_APP_SPOONACULAR_API_KEY` is embedded into frontend requests and URLs. | A configured key is public in the bundle/network requests; `.env` cannot hide client secrets. | Removed the key-dependent client integration. Manual serving-level nutrition works without a third-party service. A future food search must use a server proxy. Rotate any previously deployed key. |
| High | Direct `JSON.parse` calls throughout contexts, login and schedules; storage writes have no error handling. | Corrupt storage or quota errors can crash the app or silently fail persistence. | Validated API records and explicit failure states. Atomic file replacement; invalid existing database fails startup instead of being silently reset. Forms stay open on failed writes. |
| Medium | `Workouts.jsx` disables logging unless the selected date is today; `WorkoutForm` maintains its own date. | Historical tracking is obstructed and selected-date intent is lost. | Log past completed entries or future plans. Date flows directly into the shared form. |
| Medium | Schedule calendar marks are added inside the loop over completed workout dates. | With no completed workouts, planned dates have no markers. | One workout model and a filterable planned/completed journal; plans are visible without completed workouts. |
| Medium | `FilterSortBar.js` always renders a sort selector, even when no handler or options are supplied. | Broken/empty controls and possible undefined function calls. | Controlled, fully wired search, sort and filters. |
| Medium | Meals use `category` in forms/filtering but a grouping helper uses `type`. | Inconsistent grouping and labels. | One validated category enumeration. |
| Medium | Repeated `toISOString().split('T')[0]` and parsing of date-only strings mix UTC with local dates. | Entries and streaks can move to another calendar day near midnight, including in South Africa. | Local calendar date helpers; day arithmetic at local noon; date-only sorting. API allows one calendar day of timezone margin, while the client disallows future completed entries. |
| Medium | `ProgressRings.jsx`: fixed 2500 kcal/800 kcal goals, and `weight / goalWeight` is treated as goal progress. | Targets ignore the profile and weight loss can appear complete before starting. | Shared profile targets; weight progress uses `(current - start) / (goal - start)`, clamps bounds, handles gain/loss/equal/missing goals. |
| Medium | `UserProfileForm.jsx` displays converted pounds but saves the entered pounds as `initialWeight` without converting back. | Stored weight becomes incorrect and repeated conversion compounds the error. | Explicit kg/km inputs and display; removed the broken imperial toggle. |
| Medium | Progress entries have no edit/delete path or duplicate-day protection; zero and unbounded nutrition values are inconsistently accepted. | Mistakes cannot be corrected cleanly; trends can be distorted. | Shared client/server validation, per-day measurement uniqueness, edit/delete for all logs, optional body fat preserved as null. |
| Medium | `App.js` routes use `/` and `/user`, while navigation/shortcuts use `/dashboard` and `/profile`; two login modal owners exist. | Dead links and inconsistent login behavior. | Canonical routes, compatibility aliases, one session provider and authentication screen, accessible not-found page. |
| Medium | `Calender.jsx` uses invalid table structure; modals lack reliable keyboard focus management; many labels are unassociated. | Keyboard and assistive-technology use is unreliable. | Associated labels, semantic tables, native modal dialogs with focus restoration and Escape handling, visible focus indicators, skip link and responsive navigation. |
| Medium | Streak and calorie calculations are duplicated across screens; badges mutate profile state during workout state updates. | Diverging totals, stale values and impure state updates. | Pure shared domain functions and milestones derived from persisted records. Planned workouts are excluded from movement and energy totals. |
| Low | Many overlapping global selectors, duplicated profile/form styles, inline colors, dead components and boilerplate test. | Visual inconsistency and high maintenance cost; existing test does not exercise the application. | Removed the old implementation; shared UI primitives, one token-based stylesheet, real unit/integration/server tests. |
| Low | CRA-era build tooling, unrelated dependencies, stock CRA metadata and static-only deployment command. | Bloated maintenance surface and deployment model incompatible with real authentication. | Vite build, small dependency set, app metadata and a same-origin Node server serving the built app. |

Original file paths above refer to the pre-rewrite Git version, not retained runtime code. The old ZIP archives and image assets are left untouched; they are not served by the app and were not treated as deployable source.

## Security boundary and remaining deployment work

The rewrite provides a working small, single-process server, not a claim of production readiness for a public fitness service.

- Private server data is in `.data/fittrack.json`, ignored by Git and never served as static content. Writes use temporary-file replacement, and mutations clone the database so a failed write cannot partially update in-memory records. Run **one** server instance per data directory. Before scaling, replace this with a transactional database and a shared session/rate-limit store.
- Password hashing uses Node's built-in scrypt (`N=32768, r=8, p=3`, random 16-byte salts). Tokens contain 32 random bytes. See [Node crypto documentation](https://nodejs.org/download/release/v22.12.0/docs/api/crypto.html).
- Mutations require an exact allowed Origin and JSON content type, including authentication requests. No wildcard CORS. The API derives ownership from the server session and ignores client-provided ownership fields.
- Authentication endpoints allow 30 attempts per remote address per 15 minutes. This in-memory limit resets on restart; deployments behind a proxy need an explicit trusted-proxy configuration and preferably edge rate limiting. The server does not trust arbitrary forwarded IP headers.
- Production requires `NODE_ENV=production` and an HTTPS `APP_ORIGIN`. Cookies then use Secure, with HSTS enabled. Terminate TLS at a trusted reverse proxy. Restrict direct access to the upstream port. Do not run Vite's development server publicly.
- CSP blocks third-party scripts and framing. Inline styles remain allowed for chart geometry; scripts do not use inline execution or unsafe HTML rendering.
- Password reset, email verification, MFA, account deletion, encrypted backups, monitoring and disaster recovery are not implemented. Configure these before inviting public users. Passwords are not recoverable; there is intentionally no insecure client-only reset flow.
- Existing plaintext browser accounts are not trusted or silently migrated. Create fresh accounts. Original local storage is not deleted. Any future migration should explicitly select/import fitness records without passwords and validate every record. Legacy ZIP archives may contain old versions and should be reviewed separately before sharing the repository publicly.
- Nutrition is manually entered. Energy expenditure is clearly labelled an activity estimate, not total daily energy expenditure or a prescribed calorie deficit. Weight changes are not automatically classified as good or bad.

## Verification

- Frontend tests exercise signed-out/error states, session restoration, workout submission and dashboard updates.
- Domain tests cover timezone-safe date construction, leap-day arithmetic, planned-workout exclusion, deduplicated streaks, weight gain/loss goals, pace rounding, invalid dates/numbers and input normalization.
- Server tests exercise registration/login/logout, case-normalized usernames, cookie flags, hashing, token secrecy, session expiry/forgery, cross-account access denial, durable data after restart, create/edit/delete, duplicate measurements, validation, origin protection and rate limiting.
- `npm run build` produces the production client. `npm audit` reports zero known vulnerabilities in the final installed dependency tree (this is not a guarantee against unknown vulnerabilities).
- Current application checks: 21 frontend/domain/API tests and 4 server integration scenarios pass; the production build succeeds. Browser verification covered registration, workout and meal saving, totals, measurement logging, the progress chart and persistence after reload. Desktop (1440 px) and mobile (390 px) layouts were inspected; mobile page overflow was corrected. Browser checks used a separate `fittrack_qa_0928` account with synthetic records, leaving the user's account untouched.
